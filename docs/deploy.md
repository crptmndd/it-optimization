# Развёртывание API на VPS

Пошаговый чеклист. Всё, что можно было подготовить заранее, уже лежит в
репозитории: `server/docker-compose.prod.yml`, `server/Caddyfile`,
`server/.env.production.example`, `server/scripts/setup-server.sh`,
`server/scripts/backup.sh`.

Сайт при этом остаётся там же, где был: статика на хостинге reg.ru. На VPS
переезжает только API панели и база.

---

## 0. Что нужно до начала

| Что                                        | Зачем                                | Кто делает                     |
| ------------------------------------------ | ------------------------------------ | ------------------------------ |
| VPS, Ubuntu 22.04/24.04, ≥1 ГБ RAM         | там живут API и PostgreSQL           | ты (аккаунт и оплата)          |
| Доступ по SSH (root или sudo)              | развернуть сервис                    | ты                             |
| A-запись `api.it-optimization.ru` → IP VPS | Caddy проверяет домен через порт 80  | ты, у регистратора             |
| Секрет `FTP_PASSWORD` в GitHub             | иначе сайт соберётся, но не зальётся | проверить в Settings → Secrets |

DNS применяется не мгновенно. Проверить: `dig +short api.it-optimization.ru` —
должен вернуться IP сервера. **Пока не вернулся, шаг 3 делать бессмысленно**:
Let's Encrypt не выдаст сертификат.

## 1. Подготовить сервер

```bash
ssh root@IP_СЕРВЕРА
git clone https://github.com/crptmndd/it-optimization.git /opt/it-optimization
bash /opt/it-optimization/server/scripts/setup-server.sh
```

Скрипт ставит Docker, включает файрвол (открыты только SSH, 80, 443), закрывает
вход по паролю и, если памяти меньше 2 ГБ, добавляет swap — без него сборка
образа падает по OOM.

Вход по паролю отключается, **только если в `/root/.ssh/authorized_keys` уже
есть ключ**. Иначе скрипт оставит пароль и предупредит: он сам запускается по
SSH, и запрет без работающего ключа отрезал бы доступ к серверу.

Проверять запрет надо `sshd -T`, а не `grep` по конфигу:

```bash
sshd -T | grep -i passwordauthentication   # должно быть no
```

Причина в том, что `sshd_config` подключает `sshd_config.d/*.conf`, файлы
читаются по алфавиту, и **выигрывает первое встреченное значение параметра, а не
последнее**. Облачные образы кладут туда `50-cloud-init.conf` с
`PasswordAuthentication yes`, поэтому наш файл называется `00-hardening.conf` —
чтобы прочитаться раньше. Запрет с большим номером (или прописанный в самом
`sshd_config`, который читается после папки) не сработает и никак об этом не
сообщит. Ровно так и вышло на первом сервере: файл лежал две недели, `grep`
показывал `no`, а сервер принимал пароли и ловил ~2900 попыток подбора в сутки.

## 2. Заполнить переменные

```bash
cd /opt/it-optimization/server
cp .env.production.example .env
openssl rand -base64 24     # пароль для POSTGRES_PASSWORD
openssl rand -base64 32     # ключ для VAULT_KEY
nano .env
```

`VAULT_KEY` шифрует пароли из «Доступов» и секреты 2FA. Копию сразу сохранить вне
сервера: в бэкап базы ключ не попадает, а его потеря — это потеря всех паролей.

`GITHUB_TOKEN` на этом шаге **оставить пустым** — публикация будет работать
вхолостую, и можно спокойно проверить всё остальное, ничего не закоммитив в
боевой репозиторий.

## 3. Запустить

```bash
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml ps        # все healthy?
curl https://api.it-optimization.ru/health          # {"ok":true}
```

Первый запуск дольше остальных: собирается образ и выпускается сертификат.
Если `/health` не отвечает — `docker compose -f docker-compose.prod.yml logs caddy`
покажет, получилось ли подтвердить домен.

## 4. База и учётная запись

```bash
CO="docker compose -f docker-compose.prod.yml"
$CO exec api npx prisma migrate deploy    # таблицы (при старте накатываются и сами)
$CO exec api npm run seed:prod            # кейсы и статьи из content/*.json
$CO exec -it api npm run user:create:prod -- ТВОЯ_ПОЧТА owner
```

Пароль вводится интерактивно, в историю команд не попадает. Минимум 12 символов.

Проверить, что данные на месте (снапшот без входа не отдаётся):

```bash
$CO exec db sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) FROM cases"'
```

## 5. Переключить панель

В GitHub: **Settings → Secrets and variables → Actions → Variables → New variable**

```
NEXT_PUBLIC_ADMIN_API_URL = https://api.it-optimization.ru
```

Затем запустить workflow «Deploy to reg.ru» (вкладка Actions → Run workflow) или
просто сделать любой пуш в `main`. Адрес API запекается в статику на этапе
сборки, поэтому без пересборки панель останется в старом режиме.

После сборки `/panel` открывается формой входа. **Проверить с телефона** — ради
этого всё и делалось.

## 6. Включить публикацию

Убедившись, что вход, редактирование и загрузка картинок работают:

```bash
nano .env                                    # вписать GITHUB_TOKEN
docker compose -f docker-compose.prod.yml up -d
```

Токен — fine-grained PAT: только репозиторий сайта, `Contents: read and write`.
Теперь «Опубликовать» коммитит снапшот, GitHub Actions пересобирает сайт и
заливает его по FTP.

## 7. Бэкапы

```bash
crontab -e
0 4 * * * cd /opt/it-optimization/server && bash scripts/backup.sh >> backups/backup.log 2>&1
```

Через сутки проверить, что дампы появляются, и **один раз восстановить** — дамп,
который ни разу не разворачивали, бэкапом не является. Команды восстановления —
в конце `scripts/backup.sh`. Восстанавливать можно только в чистую схему и при
остановленном API: поверх базы с более новой схемой дамп ляжет частично, а `psql`
закончит с кодом 0.

## Обновление кода

```bash
cd /opt/it-optimization && git pull
cd server && docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml exec api npx prisma migrate deploy
```

Тома `db-data`, `uploads` и сертификаты переживают пересборку.

### Первый выкат с 2FA и паролями на сервере

`VAULT_KEY` должен оказаться в `.env` **до первого старта новой версии**. Без него API
запустится, но пароли и 2FA работать не будут.

Сначала проверить диск. Когда меняется `package.json` или базовый образ, слои `npm install`
собираются заново. Сам образ весит около 1,15 ГБ, но с промежуточными слоями и базой
`node:22-alpine` сборка на этом VPS съела 2,2 ГБ: на выкате 02.11.2026 свободное место упало
с 2,4 ГБ до 171 МБ. Нужно свободных 2,5 ГБ **после** бэкапа. Старый образ сохраняется под
своим именем: это откат без сборки и ещё 1,1 ГБ.

```bash
cd /opt/it-optimization/server
docker system df
docker image tag server-api:latest server-api:before-crm-fixes   # откат без сборки
bash scripts/backup.sh                # бэкап до выката
df -h /                               # свободно не меньше 1,5 ГБ
openssl rand -base64 32               # вписать в .env как VAULT_KEY, копию вне сервера
nano .env                             # там же CRM_ORIGIN=https://crm.it-optimization.ru
```

Места мало — сначала `docker builder prune -af`: кэш сборки уйдёт, а образ под тегом
останется. Без `-a` чистится только часть кэша. Удалять этот образ до конца выката нельзя:
без него и без кэша откат тоже потребует полной сборки. Сборка, упавшая с `ENOSPC`,
оставляет диск почти полным рядом с работающим Postgres, поэтому кэш чистится сразу, а не
после разбора.

Порядок важен, потому что CRM и сайт уезжают сами при пуше в `main`, а API обновляется
руками:

1. Запушить ветку `crm-fixes`: workflow смотрят только на `main`, поэтому пуш ничего не
   выкатывает.
2. Выкатить API из ветки. Раздел «Обновление кода» здесь не подходит: на `main` команда
   `git pull` ответит `Already up to date`, сборка пройдёт без ошибок, и API останется
   старым. Новый API работает и со старой CRM, и со старой панелью.

   Собирать и переключать лучше отдельно: старый API работает всё время сборки, а диск
   можно освободить до замены контейнера. `--no-deps` оставляет на месте базу и туннель.

   ```bash
   cd /opt/it-optimization && git fetch origin && git checkout crm-fixes
   cd server && docker compose -f docker-compose.prod.yml build api
   docker builder prune -af
   docker compose -f docker-compose.prod.yml up -d --no-deps --no-build api
   ```

3. Убедиться, что отвечает именно новый API. `/health` и вход этого не покажут, они есть и
   у старого:

   ```bash
   curl -s -o /dev/null -w '%{http_code}\n' https://api.it-optimization.ru/auth/2fa/status
   ```

   Должно быть `401`. Ответ `404` значит, что API старый, и сливать в `main` нельзя: новая
   CRM на старом API не открывает «Сегодня» и «Проекты». Дальше проверить `/health` и вход.
   На первом тике планировщик создаст счета и акты за текущий месяц и напишет в чат. Это
   ожидаемо: заведённые вручную записи не дублируются.
4. Слить в `main`: уедут CRM (быстро) и панель (около 15 минут). Пока CRM не уехала,
   «Подключить телеграм» в старой вкладке отвечает «Введите пароль»: кнопка заработает
   после обновления страницы.
5. **Включать 2FA только после того, как уехала панель и у всех обновилась CRM.** Старая
   панель не понимает билет, и человек с 2FA застрянет на её форме входа, а старая CRM
   покажет пустую страницу. Включение 2FA снимает привязку телеграма: её надо сделать заново.
6. Завести учётки, заполнить Telegram-ники в Настройках → Команда, включить 2FA, нажать
   «Перенести пароли» в «Доступах». Чат для задач — тот же `TELEGRAM_TEAM_CHAT_ID`.
7. Проверить `GITHUB_OWNER` в `.env` и переменную `NEXT_PUBLIC_ADMIN_REPO_OWNER` в Actions:
   заданное там явно значение перекрывает умолчание `crptmndd`.
8. Вернуть сервер на `main`. Иначе следующие `git pull` будут отвечать
   `Already up to date` и правки из `main` на сервер не приедут. Коммит тот же, что уже
   собран, поэтому пересборка не нужна:

   ```bash
   cd /opt/it-optimization && git checkout main && git pull
   ```

9. Когда выкат устоялся, освободить диск: `docker image rm server-api:before-crm-fixes`.

После выката разобрать старые договоры, работе они не мешают:

- договоры с галочкой «счёт каждый месяц» продолжают идти помесячно, этапы у них скрыты.
  Если договор на самом деле платится этапами, снять галочку в карточке:
  `SELECT title FROM projects WHERE work_type = 'contract' AND billing_monthly AND deleted_at IS NULL;`
- у договора с неоплаченным ручным счётом сначала закрыть или удалить счёт и только потом
  вписывать суммы этапов, иначе один долг посчитается дважды.

## Если что-то не так

| Симптом                                         | Где смотреть                                                      |
| ----------------------------------------------- | ----------------------------------------------------------------- |
| `/health` не отвечает                           | `docker compose -f docker-compose.prod.yml logs api`              |
| Нет сертификата                                 | `logs caddy` — чаще всего DNS ещё не применился                   |
| Вход проходит, но панель сразу разлогинивает    | `COOKIE_SECURE`, `COOKIE_DOMAIN`, `WEB_ORIGIN` в `.env`           |
| CORS-ошибка в консоли браузера                  | `WEB_ORIGIN` не совпадает с адресом сайта посимвольно             |
| «Опубликовать» пишет про отсутствие доступа     | пустой или просроченный `GITHUB_TOKEN`                            |
| Сайт не обновился после публикации              | Actions: собралось ли, и задан ли секрет `FTP_PASSWORD`           |
| Пароли не открываются, 503 `vault_unavailable`  | `VAULT_KEY` в `.env`, после правки пересоздать контейнер          |
| В логе `VAULT_KEY не подходит к записям в базе` | Опечатка в ключе. Новые пароли не сохранять, вернуть прежний ключ |
| Потерян телефон и коды восстановления           | `$CO exec api npm run user:reset-2fa:prod -- ПОЧТА`               |
| Бот молчит о задачах                            | `TELEGRAM_TEAM_CHAT_ID`, бот в чате, контейнер `tg-tunnel`        |
| API в перезапусках, в логе `P3009`              | Дамп лёг поверх новой схемы. Повторить по `scripts/backup.sh`     |
| Сборка упала с `ENOSPC`                         | Сразу `docker builder prune -f`: рядом работает Postgres          |

## Откат

Панель возвращается в прежний режим за одну минуту и без сервера: удалить
переменную `NEXT_PUBLIC_ADMIN_API_URL` и пересобрать сайт. `/panel` снова
попросит токен GitHub и будет коммитить напрямую. Публичные страницы не зависят
от API вообще — они статические, и падение сервера на них не влияет.

### Откат выката с 2FA и паролями на сервере

**Сначала CRM, потом API.** Новая CRM не работает со старым API: «Сегодня» и «Проекты»
показывают «Раздел не открылся», «Счета» отвечают «Некорректные данные», «Настройки» —
«Not Found». Пересборка CRM стоит в той же очереди `deploy-production`, что и заливка
сайта, поэтому при откате API первым вернуть её быстро не получится.

1. Сделать revert в `main` и дождаться конца обоих workflow: revert, задевающий `src/`,
   запускает и CRM, и сайт (около 15 минут).
2. Вернуть API. Из сохранённого образа, без сборки:

   ```bash
   cd /opt/it-optimization && git checkout main && git pull
   cd server
   docker image tag server-api:before-crm-fixes server-api:latest
   docker compose -f docker-compose.prod.yml up -d --no-build api
   ```

   Образа нет — те же команды без `image tag` и с `--build`: кэш сборки покрывает старый
   код, а без него нужно 1,15 ГБ свободных.

Если 2FA уже включена, откат CRM закрывает вход людям с 2FA: старая CRM не знает второго
шага и после пароля показывает пустую страницу. Открытые сессии при этом работают. Пока
панель не откатилась, можно войти через `/panel`: кука общая, и старая CRM с ней откроется.
Откатилась и панель — снять 2FA: `$CO exec api npm run user:reset-2fa:prod -- ПОЧТА`.
Пустая страница из-за старой CRM в кэше браузера лечится обновлением страницы.

После отката это не поломки, данные целы:

- задачу и проект с Тимуром старая форма не сохраняет, отвечает «Некорректные данные»:
  старый API знает троих, а в его форме Тимура не снять. Смена статуса проходит;
- архивные проекты снова видны в списке и на доске: фильтра архива в старом коде нет;
- этапы и пароли, введённые после выката, не видны, строки остаются в базе.

**Откат API на версию без 2FA выключает её молча:** старый `/auth/login` пускает по одному
паролю, а `GET /credentials` снова отдаёт `secret` всем вошедшим. Поэтому такой откат —
осознанное решение на короткое время. База не откатывается: миграция только добавляет, и
старый код с ней работает. Перед возвратом на новую версию отозвать сессии, созданные за
время отката, потому что они вошли без второго фактора:

```sql
UPDATE sessions SET revoked_at = now()
WHERE revoked_at IS NULL AND created_at > '<время отката>';
```
