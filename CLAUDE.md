# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Marketing landing site for the IT company «Айти-Оптимизация» (it-optimization.ru). Russian-only. There is no contact form — leads are captured through direct links into messengers (Telegram, WhatsApp, MAX), phone, and email. The public site itself has **no server runtime**; the only backend is the admin API in `server/` (see «Backend» below), which the public pages never call. The whole site is a **static export** (`out/` folder of plain HTML/CSS/JS) uploaded to shared hosting.

## Commands

```bash
npm run dev      # dev server at localhost:3000
npm run build    # runs scripts/generate-og.mjs, then `next build` → static export to out/
npm run start    # serve a production build via Node (not used for deploy — export is static)
npm run lint     # ESLint (next lint)
npm run format   # Prettier over src/**/*.{ts,tsx,css,json}
```

There is **no test suite**. Verify changes by running `npm run dev` (or `npm run build` for export-only issues) and inspecting the site.

Utility scripts (run manually, not part of normal dev):

- `node scripts/generate-og.mjs` — composites `public/LOGO.svg` onto a 1200×630 canvas → `public/og-image.webp` (also runs automatically before every build).
- `node scripts/convert-cases.mjs` — converts new PNGs in `public/cases/` to WebP and deletes the PNGs.
- `python scripts/ftp-upload.py` — uploads `out/` to reg.ru hosting over FTP (needs `FTP_PASSWORD` env var). This is the deploy step; `.github/workflows/deploy.yml` runs exactly this on every push to `main` (secret `FTP_PASSWORD`), which is what makes the /panel panel self-publishing. Running it locally still works and is interchangeable. Uploading alone never deletes anything, so after the upload it prunes the data-driven sections — `blog`, `uslugi` and their `en`/`es` twins, one level deep — of whatever the fresh build no longer has: before that, a post deleted or renamed in /panel kept answering 200 at its old address forever. Nothing outside those sections is touched (search-engine verification files, documents uploaded by hand), and the CRM deploy, which sets `FTP_LOCAL_ROOT`, prunes nothing unless `FTP_PRUNE_DIRS` says so.

## Architecture

**Framework:** Next.js 15 App Router, React 19, TypeScript, Tailwind CSS 4. Import alias `@/*` → `src/*`.

**Static-export constraints (`next.config.ts`):** `output: "export"` — no server runtime, so no API routes, no server actions, no `next/image` optimization (`images.unoptimized: true`), no runtime env reads. `trailingSlash: true` makes each route a folder with `index.html` so clean URLs resolve without rewrites. Any new dynamic route must be fully enumerable at build time via `generateStaticParams`.

**Routes (`src/app/`):**

- `/` (`page.tsx`) — the one-page homepage. Composes section components; every section below the hero is `dynamic()`-imported and wrapped in a `.section-defer` (content-visibility) div for lazy rendering.
- `/uslugi/[slug]` — one SEO page per service. Slugs are **not** free-form: they come from `SERVICE_PAGES` in `src/lib/constants.ts` (service key → slug), `dynamicParams = false`, and `generateStaticParams` enumerates them. Adding a service page = add an entry to `SERVICE_PAGES`, a record to `content/services.json` (the page body, see «Service pages» below) **and** a `services.items.<key>` block in `messages/ru.json` (the card: title, budget, deadline, tags).
- `/proekty` — projects/cases catalog.
- `/panel` — content panel: cases and blog (see «Admin panel» below). Shipped in the export but `noindex` + disallowed in `robots.ts` and deliberately absent from `sitemap.ts`.
- `/blog` + `/blog/[slug]` — blog listing and per-article pages. Posts are **data**, not code: the ordered array in `content/blog.json` is the source of truth and `generateStaticParams` enumerates it (`dynamicParams = false`). Nothing about an article lives in code any more — adding or editing one is done in /panel, and covers land in `public/blog/` (the first three are hand-drawn SVGs, panel uploads are WebP).
- `global-not-found.tsx` — the 404 for the whole site (flag `experimental.globalNotFound`; with two root layouts a plain `not-found.tsx` never reaches the export). One `out/404.html` serves every locale: an inline script sets `data-locale` from the path before paint, and `NotFoundExperience` renders only that locale (strings for all three arrive as props, because no next-intl provider exists there; only one language is ever in the DOM). Whether the host actually serves it is server config, not code: either nginx `error_page 404 /404.html;`, or Apache reading `public/.htaccess`, which already carries `ErrorDocument 404` and `403` (per-locale 403 under `<IfVersion>`, tested on a real Apache 2.4). Today neither applies, and on the current tariff neither can: it is reg.ru Host-Lite, the one plan with no Apache handler, and nginx config is never open to customers on shared hosting (support confirmed, 2026-10-07). So nginx serves the files directly, ignores `.htaccess` and shows its own stub — still with an honest 404 status, so search is unaffected. The pages start working on any other reg.ru tariff, or if the static site moves to the VPS; do not suggest asking support again.
- `/403` (+ `/en/403`, `/es/403`) — `views/forbidden-page.tsx`. A plain route, not `forbidden()`: that needs a server runtime. The HTTP status must come from the web server. Both error pages are one `ErrorScreen` (`src/components/error-pages/`), laid out after the owner's Figma: no header and no scroll (a fixed full-viewport frame), the logo right above the code, the code in huge striped digits — black, the zero brand-green and turned into an emblem (a round magnifier with a thin straight handle on 404 — the font's oval zero with a thick rounded handle read as anything but a magnifier — and a padlock with a keyhole on 403) — then one line and «На главную» in one row, mirrored between the two pages, and blurred copies of the digits in the corners. The whole composition is sized by one width, `--dw`, capped by both viewport width and height, so a short laptop shrinks it instead of scrolling. The digits are cut from the site font at load (`striped-code.tsx`; the emblem is drawn into the same mask, so it is sliced into the same stripes) and run on the same `PluckedStripes` engine as the footer wordmark (`src/components/ui/plucked-stripes.tsx`), so they pluck under the pointer exactly like it, and under a finger too. Both are `noindex` and out of the sitemap.
- `robots.ts`, `sitemap.ts` — generated SEO endpoints.

**Content / i18n:** All user-facing copy lives in `messages/ru.json` and is read through `next-intl`. This is a **single-locale (RU) setup used purely as a string catalogue** — no i18n routing, no locale switching, no middleware (`src/i18n/request.ts` hardcodes `"ru"`). Never hardcode Russian strings in components; add them to the catalog and read with `useTranslations` / `getTranslations`. Four deliberate exceptions: **cases** (`content/cases.json`), **blog posts** (`content/blog.json`), **service page bodies** (`content/services.json`) — all editable content, see below — and the **/panel** UI, whose labels are hardcoded in `src/components/admin/` because the catalog is loaded on every public page and the panel is an internal tool.

The reason those three left is the same one, and it is the load-bearing fact about this catalog: `layout.tsx` hands the **whole** of `messages/ru.json` to `NextIntlClientProvider`, so every byte of it is serialized into **every** page of the export. Long-form copy in the catalog is therefore paid for by pages that never render it — the blog kept only chrome (headings, «читать далее»), and the service pages kept only `servicePages.common` (the shared section titles and button labels). Anything that belongs to one page and runs to hundreds of words goes into `content/`, not here.

**Cases (portfolio):** Cases are data, not code — the ordered array in `content/cases.json` is the single source of truth. Its shape deliberately mirrors the future `cases` table (`id` uuid, `slug`, `title`, `description`, `quote`, `tags: string[]`, `cover`, `detail`, `detailMobile`, `createdAt`, `updatedAt`) so the move to PostgreSQL is a data transfer, not a reshape. Array order is the order on the site; the homepage teases the first `HOME_CASE_COUNT`. Artwork lives in `public/cases/`.

Reads go through **one seam**: `src/lib/cases/repository.ts` (`CaseRepository`, JSON-backed today, Prisma tomorrow). Its methods are async on purpose. Server components fetch (`getAllCases()`, `getHomeCases()`) and **pass cases down as props** — no client component imports the JSON, which is what lets the source become a database later. `pickCases()` resolves a list of slugs in order and silently drops unknown ones, so a case deleted in /panel can never break the build. Tags are stored as a list and joined with `TAG_SEPARATOR` via `formatTags()` for display.

**Blog (`content/blog.json`):** Same shape of decision as cases, for the same reason — the panel can only edit data. One ordered array (`id`, `slug`, `title`, `excerpt`, `category`, `lead`, `metaTitle`, `metaDescription`, `cover`, `readingTime`, `sections: [{heading, body: string[]}]`, `takeaways`, `services`, `publishedAt`, `createdAt`, `updatedAt`), mirroring the `posts` table in `server/prisma/schema.prisma`. Array order is the order in the blog. Reads go through `src/lib/blog/repository.ts`; server components fetch (`getAllPosts()`, `getPostBySlug()`, `getPostsForService()`) and pass posts down as props.

Two fields are derived rather than stored, because a second stored copy eventually disagrees with the first: the displayed date («18 июля 2026») comes from `publishedAt` via `formatPostDate()`, and `estimateReadingTime()` only _suggests_ `readingTime` in the panel — the number itself is stored and editable, since an article full of lists reads faster than its word count says. `services` (the SEO cross-link between an article and the service pages it is about) lives **on the post**: it used to be `RELATED_ARTICLES` plus a derived reverse map in `constants.ts`, and a map in code cannot be edited from the panel.

**Service pages (`content/services.json`):** The body of every `/uslugi/<slug>/` page — one ordered array (`key`, `slug`, `metaTitle`, `metaDescription`, `breadcrumb`, `h1`, `lead`, `includes`, `forWhom`, `steps`, `faq`, `tariffs?`), same decision as cases and blog. These texts used to be the `servicePages.<key>` block of `messages/ru.json`, which meant ~3 KB of tariffs and FAQ per service riding along on the homepage, the blog and every other page; moving them out cut the catalog from 163 KB to 39 KB. Reads go through `src/lib/services/repository.ts` (`getServicePageBySlug()`), and the route passes the single record down as the `servicePage` prop — the client component takes `import type` only, so the JSON never reaches the browser bundle.

The identifier here is `key`, not a uuid: it is the join key four other things already point at — `services` on a case, `services` on a post, the 3D hero scene in `HERO_VISUAL`, and `Lead.service` in the CRM. Renaming one means renaming all five. `slug` is deliberately duplicated between this file and `SERVICE_PAGES`, because the constant is imported by client components (header menu) that must not pull the whole file in; the route turns a divergence into a **build failure** with the offending slug named, since `notFound()` would have made it a silent 404. `tariffs` is optional — a service without fixed packages simply renders no tariff block and no `AggregateOffer` in its JSON-LD.

**Service catalog (`content/service-catalog.json`):** The _structure_ of `/uslugi/` — an ordered list of categories (`key`, `title`) and an ordered list of services (`key`, `slug`, `category`, `draft`) — kept in a separate, deliberately tiny file (~5 KB) from the page bodies. `src/lib/constants.ts` derives `SERVICE_PAGES`, `SERVICE_CATEGORIES`, `SERVICE_CATEGORY_NAV`, `SERVICE_NAV` and `DRAFT_SERVICES` from it and hardcodes none of them, so a service can never be in the catalog but missing from the header menu: one list, one order, and a service without a category simply does not appear anywhere.

The split is the point. Client components — the header menu, the service card, the catalog page — import this file; they must never pull `content/services.json`, which carries the text of thirty-plus pages. Anything the browser needs about _every_ service goes here; anything belonging to _one_ page goes there.

A category is a **filter chip, not a route** (`src/components/ui/filter-chips.tsx`; below `md` the same filter is the `FilterSelect` dropdown from /proekty, because eight chips wrap into half a phone screen and push the catalog itself out of view): the catalog is one grid with a row of buttons over it, not eight stacked sections — a page cut into eight lists is read as eight lists, and the visitor who came for one service still scrolls past seven foreign ones. Filtering does not change the URL, so `/uslugi/` stays one page for search rather than multiplying into eight near-identical ones. Nobody searches «Дизайн и интерфейсы» anyway; a category earns its own page only once a real query exists for it («услуги информационной безопасности»), and that is a separate decision. A category left with only drafts is dropped whole by `SERVICE_CATEGORY_NAV` — a button opening an empty grid reads as a bug.

A service whose catalog entry has `draft: true` is one whose page is still being written. Its page **builds and opens at its own URL** — that is how it gets reviewed — but it is filtered out of `SERVICE_CATEGORY_NAV` and therefore out of the catalog, the header menu, `SERVICE_NAV`, the sitemap and the `ItemList` JSON-LD; the route gives it `robots: noindex`, and `RELATED_SERVICES` entries pointing at it are dropped so no published page links to it. A category left with only drafts is hidden whole, since a heading over an empty grid reads as «заявлено, но нет ни одной услуги». This exists because deploy is automatic on push to `main`: without the flag, every half-written page would ship with the next commit. Publishing a service is one checkbox in /panel.

**Admin panel (`/panel`):** Lets an admin add/edit/delete/reorder cases **and blog posts**, and rearrange the **service catalog**, from any device — three tabs over one login (`admin-panel.tsx` is the shell holding auth and the tab; `cases-panel.tsx` / `blog-panel.tsx` / `services-panel.tsx` are the sections, `panel-chrome.tsx` the shared header, fields and publish notices). All sections stay mounted so switching tabs never drops an unfinished edit.

The **Услуги** tab edits `content/service-catalog.json` and nothing else: categories (add, rename, reorder, delete-when-empty), which category a service sits in, its order inside that category, and its draft flag. Page bodies are deliberately absent — twelve fields across thirty-plus pages is a text editor, not a panel, and those texts change far less often than the shelf they stand on. A new category's key is generated from its title in camelCase (`ServicesPanel.categoryKey`, not `slugify()` — the server wants `^[a-zA-Z][a-zA-Z0-9]*$`, and a dash would fail validation) and stops following the title after the first publish, since services already point at it by key. It runs in one of two modes (see «Backend» below). In **API mode** (current production) an admin logs in with email and password, plus a one-time code if the account has 2FA (see «Two-factor login» below). In **token mode** — the fallback when no API is configured — the key is a GitHub fine-grained PAT pasted once and kept in `localStorage`. The panel processes picked images in-browser to the exact WebP geometry the site expects (`src/lib/admin/images.ts` — cropped square case cover, letterboxed 16:9 and 9:16 slides, cropped 1200×750 post cover, content-hashed filenames so replacements dodge browser caches), then writes `content/cases.json` (or `content/blog.json`) plus the new assets in **one atomic commit**. Writes also go through a seam: the panel talks to `CasesApi` (`src/lib/admin/cases-api.ts` — `load()` / `publish()` with an opaque `version` for optimistic locking) and the mirroring `BlogApi` (`src/lib/admin/blog-api.ts`) and `ServicesApi` (`src/lib/admin/services-api.ts`), whose GitHub implementation is the Git Data API (`src/lib/admin/github.ts`: blobs → tree → commit → ref, refusing to publish if the branch moved meanwhile). The push triggers `.github/workflows/deploy.yml`, which rebuilds the export and FTP-uploads it — so cases stay prerendered in static HTML and SEO is unaffected. Panel writes are the _only_ thing that needs the token; unauthenticated visitors to `/panel` can do nothing.

**Backend (`server/`):** A separate Fastify + Prisma + PostgreSQL service that backs the panel: login/password auth (Argon2id, server-side sessions in an httpOnly cookie), case and blog-post CRUD, service-catalog editing, image upload re-encoded with sharp, and publishing. Cases, posts and the service catalog each carry their own revision counter (`content_revisions.scope`) — one shared counter would reject an untouched case edit just because a post was saved next to it.

The catalog lives in two tables mirroring the two arrays of the JSON file (`ServiceCategory`, `ServiceEntry`; `server/src/services/routes.ts`). `ServiceEntry.key` is the primary key rather than a uuid, because that key is what four other things already point at. The relation is `onDelete: Restrict`: deleting a category must not take the service pages that stood in it. `PUT /service-catalog` replaces both lists in one transaction, upserting categories _before_ services and deleting stale categories _after_ them, so nothing ever references a row that does not exist yet. `npm run seed` is additive for the catalog on purpose — it fills in services missing from the database but never overwrites an assignment made in the panel, otherwise every seed would roll the editor's work back to the file in the repo. **It is deployed** at `https://api.it-optimization.ru` (VPS, Docker Compose: Caddy → API → Postgres, Let's Encrypt, daily `pg_dump` backups). Which mode the panel uses is decided by one env var: `NEXT_PUBLIC_ADMIN_API_URL` set → `httpCasesApi` + login form; unset → `githubCasesApi` + token. Both satisfy the same `CasesApi`, so nothing else in the panel knows the difference. Run it locally per `server/README.md` (needs Docker); architecture and rationale are in `docs/backend.md`. Production configs are in use: `server/docker-compose.prod.yml` (Caddy → API → Postgres, only 80/443 exposed), `server/Caddyfile`, `server/.env.production.example`, `server/scripts/{setup-server,backup}.sh`, and the step-by-step checklist in `docs/deploy.md`. The switch is a repo **variable**, not code: setting `NEXT_PUBLIC_ADMIN_API_URL` in Actions makes the next build ship the login-form panel; deleting it reverts to token mode.

Even with the backend, the public site stays a static export: PostgreSQL is the editing source of truth, and publishing commits a snapshot of `content/cases.json` / `content/blog.json` (plus new assets) to the repo, which triggers the same rebuild-and-FTP workflow. Keep each snapshot, its type (`src/lib/cases/types.ts`, `src/lib/blog/types.ts`) and `server/prisma/schema.prisma` in sync — that is one contract per section, and `npm run seed` relies on it. Seeding the blog is not optional in API mode: an empty `posts` table would wipe the blog off the site on the first publish.

**CRM (`crm/`):** The team's internal system — today's work, projects, tasks, clients, invoices, credentials — at `crm.it-optimization.ru`. A **separate Vite + React SPA**, not a route of the site: the site is a static export with no runtime, while a CRM needs server-side lists, filters and per-request auth. What they share is the backend — same API, same PostgreSQL, same `users`/`sessions`, so one login covers both `/panel` and the CRM (the cookie is issued on `.it-optimization.ru`, and `WEB_ORIGIN` in `server/.env` is a **comma-separated list** of origins because CORS with `credentials` rejects `*`). No SSR on purpose: the app is behind a login, so rendering it on a server buys nothing and costs a Node process. Deploy is `.github/workflows/deploy-crm.yml` → `crm/dist` over FTP to the subdomain, reusing `scripts/ftp-upload.py` via `FTP_LOCAL_ROOT`/`FTP_REMOTE_ROOT`, in its own concurrency group `deploy-crm` — it used to share `deploy-production` with the site, and since GitHub keeps only one pending run per group, a site run queued right after silently cancelled the CRM run of the same push; `crm/public/.htaccess` supplies the SPA rewrite. The look: a grey canvas with white cards, no border around each row (`List` holds rows in one card), one lime primary button per screen, repeated row actions as `secondary`, `Segmented` for slices and views, round `PeopleFilter` for a person. The left panel is `w-64` and from `md` up collapses to 72px of icons (the button in its header or `Cmd/Ctrl+B`, kept in `localStorage`, a 200 ms width transition that `prefers-reduced-motion` turns off); a phone has a bottom tab bar instead. `/tasks` and `/projects` take the full width of the window (`FULL_WIDTH` in `shell.tsx`), the other screens stop at `max-w-[1280px]`. There is a dark theme: Settings → «Оформление» offers system (default), light or dark, kept per device in `localStorage` (`crm.theme`), applied as `data-theme` on `<html>` by an inline script in `crm/index.html` before first paint and then by `crm/src/lib/theme.ts`. Colours come only from the tokens in `crm/src/styles.css`, each defined for both themes; translucent overlays use `bg-ink/…` (black in light, white in dark), never `bg-black/…`, and the `dark:` variant covers the rest. The 2FA QR code stays on white on purpose. Native date inputs are replaced by `DateField` (same `YYYY-MM-DD` value), so it swaps in without changes around it. All three dropdowns share `components/dropdown.ts`; the panel is portalled to `body`, otherwise a modal's `overflow-y-auto` clips it. A new task has no status field: it starts as `todo`, or in the status column whose «+» was pressed. A screen that throws shows «Раздел не открылся» with the menu still alive (`ScreenBoundary` around `<Outlet />`), not a blank page; during a rollback the usual cause is a new CRM on an old API, which is why the order is CRM first, then API (`docs/deploy.md`). A rollout goes the other way, API first: a new CRM reads the old API's `role: "owner"` as not an admin and hides every admin section. Details in `crm/README.md`.

**Working with tasks from Telegram (`notify/task-actions.ts`, `notify/intake/reply.ts`, `notify/questions.ts`, `notify/reminders.ts`):** every message about a task carries buttons: «✅ Готово» and «▶️ В работу», then «📅 Изменить срок» and «📎 Прикрепить файл»; a closed task gets «↩️ Вернуть в работу» instead of «Готово» (`taskActionRows`/`taskKeyboard`; a subtask gets only the status button, since the CRM shows nothing else on it). The creation card puts its own «Исполнители» and «Отменить» between these rows and the CRM link. «Изменить срок» and «Прикрепить файл» ask instead of acting (`notify/pending.ts`): the bot asks «Когда срок?» or for a file with a force-reply prompt, and the person's next message in that chat is the answer, checked before intake so that «до ноября» in a private chat does not become a new task. In the team chat only a reply to the prompt counts (it reaches the bot under Group Privacy too, and a stray remark never becomes a date); a command or «отмена» drops the wait, which lives in memory for ten minutes. Common forms («завтра», «25.11», «без срока») are parsed without the model; the rest («до ноября» → 31 October, «к пятнице» → that Friday, «через две недели») goes to the model, and `dueFrom` rejects anything unreal, past or more than two years out — a date understood but already past says so instead of «не понял». Files from an album arrive as several messages, so the confirmation waits two quiet seconds and counts them all. After either, the original task message is re-rendered in its own kind (`refreshTaskMessage` in `notify/task-view.ts`: card, task from a list, or notification). The old «📅 На завтра» (`s:tmrw`) still works on messages sent before it was replaced. A press goes through `updateTask` in `crm/tasks/service.ts`, the very function behind `PATCH /tasks/:id`, so only someone who can see the task in the CRM can press, and columns, `completedAt` and the hand archive follow the same rules; the message is then re-rendered from the database, so the team chat sees who closed it. Notifications after any change, from the form or from Telegram, go through one `afterTaskUpdate`: newly added people are notified, and a top-level task closed by someone other than its author is reported to the author privately — the author used to learn of it only by opening the CRM. `/tasks`, the evening deadlines and question answers number their lines, and a number opens that task **in place of the list** (`o:<kind>:<id>`) with «⬅️ Назад» left of «Открыть задачу» (`b:<kind>`), which rebuilds the same list in the same message, so a task just closed is already gone from it and the chat does not grow with every opened task. My tasks and deadlines are rebuilt from the database; a question does not fit into 64 bytes of button data, so it is remembered in memory by message id (`rememberQuestion`), and after a restart «Назад» falls back to my tasks.

A reply to any bot message about a task (notification, card, task from `/tasks`) is a conversation about that task, not a new one: the model lays it out as a comment, a status, a due date, people to add or remove, a title or new subtasks, and the human's own words, not a paraphrase, become the note. A plain reaction («ок», «спасибо») changes nothing and the bot stays silent, since it must not answer every «ок» in the team chat. Two rules live in code because the model would not keep them: a person named for a new subtask is not added to the task itself, and a new message becomes a subtask of an existing task only when the author says so explicitly («подзадача», «в задачу…», «пункт») or replies to its card (`EXPLICIT_PARENT`) — otherwise the model hooked new bugs onto any similarly named task. The same model call also tells a task from a question: «что у Вадима просрочено?», «что по кошельку?», «что я закрыл на неделе?» become a `TaskQuery`, and the list is built by code through `taskScope`, so the bot cannot invent tasks and shows exactly what the CRM would; questions are answered only in private chats, and an employee's empty answer says that only their own work is visible. At `REMINDER_TIME` (default 17:00) everyone linked gets their tasks due today and tomorrow privately; the day is marked in `job_runs` like the digest, nothing to remind means silence, and after 21:00 the day is skipped rather than sent at night.

**Task attachments (`crm/tasks/attachments.ts`, `TaskAttachment`):** screenshots and documents, mostly from Telegram (photos, documents and videos in a message become files of the created task; in a reply, of that task; a subtask's files go to its parent, which has the window), and from the «Файлы» block in the CRM task window (button or drag and drop). A file lives in `UPLOAD_DIR/attachments` under a random name (the original name never touches the path) — the same `uploads` volume `backup.sh` snapshots. It is served only through `GET /tasks/:id/attachments/:attachmentId` to someone who can see the task: there are client data in these files, and a public link would travel beyond the team. Only PNG, JPEG, GIF, WebP and PDF open inline (images with a restrictive CSP); everything else, SVG and HTML included, is forced to download as `application/octet-stream`, because opened from the API's origin it would run with the session's cookie. The DTO lives in `attachment-dto.ts` rather than next to the routes to break an import cycle with `dto.ts`. Rows cascade with the task, files do not, so the daily cleanup in `server.ts` removes files without a row that are older than a day. Voice messages are not attached: their transcript is already in the task. The board card shows «📎 Файлов: N» top-right (the project stays top-left) and the list row a paperclip with the number: `files` in `TaskDto` is a `_count` in the same query as the list, and the task window reports uploads and deletions back to the card (`onFiles`), so the mark changes without a reload.
**Notifications (`server/src/notify/`):** A Telegram bot delivers the thing that actually prevents forgetting. Delivery splits by audience, because employees sit in the team chat (`TELEGRAM_TEAM_CHAT_ID`). The **morning digest is personal** (`personalSnapshot` in `today.ts`, at the owner's request: in a team-wide digest everyone scrolled the whole team looking for their own): every linked person gets privately only their own tasks and the deadlines of their own projects, and an admin also gets the money — renewals, unbilled months, long-unpaid invoices — for the whole company, not narrowed to them, since a narrowed slice would drop a domain or invoice nobody owns. Admins also get **in private** through `notifyAdmins` and `notifyTask`: the month's generated invoices, a new project, a new lead, a 2FA lockout, and any task, subtask or project assigned to them. A task (not a project: its message names the client) also goes privately to every **employee** it is assigned to who has linked the bot, on top of the team-chat tag — at the owner's request, since a tag gets lost among other people's messages (`accountChatsOf` in `notifyTask`); the person who set or reassigned the task gets nothing privately (`skip`), having just seen it, and «Уведомление в общий чат» switches off only the chat. There is deliberately no fallback to the team chat: those messages carry money and client contacts. So an admin who has not linked the bot gets nothing, the Team list marks them «бот не подключён», and the miss is only logged. The team chat keeps employees' work: tasks tagged to an employee, and in the morning only the tasks nobody took (`unassignedSnapshot`), so that someone picks them up; no such tasks, no message. A task on both an admin and an employee goes to the chat with only the employee tagged and to the admin privately; a task only on admins skips the chat. A person with no account counts as an employee here, since there is nowhere to write to them privately. Only private chats count (`isPrivateChat`): a positive id. An old link to a group neither receives admin messages nor answers `/today`, and `/telegram/status` reports it as not connected. Task messages (`notifyTaskInBackground`) are fire-and-forget: the task is already saved and Telegram can be down or take tens of seconds, so the response never waits for it and a failure is only logged. The task form has «Уведомление в общий чат», on by default and shown only when the bot would post to the chat (an employee or a person without a login among the people, or nobody at all; on edit, only among the people just added): `notifyChat: false` on `POST`/`PATCH /tasks` skips the team chat for that one save and is written to `audit_log`, while admins still get their private message. It is not stored, so the next save notifies again. `PATCH /tasks/:id` tags only names that were not there before, because the form sends the whole list on every save and a title edit must not wake everyone; closed tasks, removed assignees and reordering stay silent. A task message has one shape everywhere, in the chat and in private, for a new task and a reassigned one, and it follows the owner's template: `📌 <b>title</b>`, then `💬 <note>` if the task has one (the latest, cut to 280 characters, read in `notifyTask` so creation and assignment share it), `🧩 В задаче: <parent>` on a subtask, then `Исполнитель: …` («не назначен» when nobody is), then `🟡 Приоритет: Обычный` (🟢 Низкий, 🟠 Высокий, 🔴 Срочно) and `📅 Срок: 24.10.2026`, left out without a due date. By the owner's choice it does not say who set the task and has no project line. Everyone on the task is listed, but in the chat only the people just added who are not admins are tagged; the title comes first, so the phone preview shows the task rather than the tag. A project message is the same shape without the level: `📁 <b>title</b>`, `Клиент:`, `Исполнитель:`, `📅 Срок:`. The digest is separate and marks only `high`, with ❗. Under the message sits a URL button into the card. The button exists only when `CRM_ORIGIN` is https: Telegram refuses the whole message over a localhost URL. A subtask's button opens the parent, and without an assignee it stays silent: it is a checklist line inside someone's card, not work waiting for an owner. The tag comes from `team_members` (a person's name → Telegram username, edited by an admin in Settings → Team). Linking the bot fills an empty username from Telegram itself and never overwrites one set in Settings. No username but a linked private chat gives a `tg://user?id=` mention, since a private chat id is the person's id; neither gives the plain name. The match between an account and a person is the `team_members.user_id` link; nothing is guessed from the name any more. The task form warns when a picked person has no username and «Кто делает» is built from the same list, which is why `GET /team/handles` is open to the team while `PUT` stays with admins. The bot runs **inside the API process on long polling** (`getUpdates`), not webhooks, so it works identically in local dev with no tunnel; the cost is that only one process may poll a given bot, so multiple API replicas would need the bot extracted. Everything is optional: no `TELEGRAM_BOT_TOKEN` → `canNotify` is false, the bot never starts, and the rest of the API is unaffected. Users link their account by requesting a short-lived code in CRM settings and sending `/start <code>` to the bot — credentials never travel through the chat. A code sent to a group is refused and burned: the whole group has read it, and any member could otherwise send it to the bot privately and link their own Telegram to someone else's account. A linked chat reads `/today` with no session at all, so the code takes the account password and `requireCrmOrigin`: otherwise a stolen cookie would leave its own chat a view that survives logout and revoked sessions. Linking and unlinking go to `audit_log`, and changing the password (`user:create`) or enabling 2FA drops the link. What `/today` shows depends on where it is asked, and it is always what the morning brings there: the team chat gets the tasks nobody took whoever asks, and a private chat the person's own digest (`personalSnapshot`, with the role read on every command, so a demotion applies at once). The CRM's Сегодня screen is unchanged and still gives an admin the whole team (`collectTodayFor`). The scheduler (`notify/scheduler.ts`) is a one-minute tick started by `server.ts`, not by the bot, with the last-run date persisted in `job_runs`, **not** in memory: an in-memory flag makes every daytime restart re-send the digest. `TIMEZONE` matters — "today" and "overdue" are calendar days in the team's zone, computed via `Intl` in `notify/zone.ts` rather than a date library. An empty digest is not sent at all; a daily "all clear" trains people to ignore the bot. «Quiet» is stricter than «empty» (`isQuietSnapshot` vs `isEmptySnapshot`): what is always there — the next stage of a running contract, an invoice sent last week, a deadline next week — appears in a digest that is already going out but never triggers one. **Telegram is unreachable from the VPS's network** — every Telegram address on every port (443, 80, 8443) is dropped at the route level, so nothing configured on the server can fix it. Egress goes through a teammate's server instead: the `tg-tunnel` service in `docker-compose.prod.yml` holds an `autossh -L 0.0.0.0:443:api.telegram.org:443` forward and carries the network alias `api.telegram.org`, so the bot's ordinary `https://api.telegram.org` requests resolve (via compose DNS) to that container and leave through the tunnel. It is a port forward rather than SOCKS because Node's built-in `fetch` has no SOCKS support, and the far side resolves the hostname, so TLS stays end-to-end between the bot and Telegram — neither side of the tunnel sees the token. New connections through it once hung 30–70 s roughly one in five: `api.telegram.org` has an AAAA record, `getaddrinfo` on the proxy host put IPv6 first, and that host's route into Telegram's IPv6 network was broken, so its sshd stalled on the first address until the kernel gave up and only then fell back to IPv4. The cure lives on the proxy host (system-wide IPv4 precedence), not in this repo — so if such hangs ever return, that is the first thing to ask about rather than something to work around here. Two traps that cost hours once: forwarding to a Telegram **IP** instead of the hostname looks like a fix but is refused (`administratively prohibited`), because the key is restricted to `api.telegram.org:443` and nothing else; and a long-lived SSH connection keeps whatever resolver order its sshd child started with, so after any change on that host the `tg-tunnel` container must be recreated before the change takes effect. The key and pinned host key live in `/etc/tg-tunnel/` on the VPS, never in the repo. The tunnel is deliberately not a `depends_on` of `api`: a dead tunnel must silence only the bot, not the CRM. Never reintroduce an `extra_hosts` entry for `api.telegram.org` — `/etc/hosts` beats compose DNS and would bypass the tunnel. If the block is ever lifted, deleting the `tg-tunnel` service is the entire rollback.

**Tasks from messages (`server/src/notify/intake/`, `server/src/ai/replicate.ts`):** the same bot turns a message into a task. In a private chat it takes everything a linked user writes, forwards or says by voice («Фиксы по кошельку Камилю до пятницы»); in the team chat only what is addressed to it: `/task …`, a reply to one of its task cards, or an @mention (Telegram delivers mentions only with Group Privacy off or the bot an admin, so `/task` is the form that always works). Ordinary group chatter is ignored outright — before this, a bot with privacy off would have answered every message with the help text. One person's messages are gathered into one bundle (2 s of quiet, 12 s when it holds only forwards, since the caption is often typed after the forward; 20 s cap), because a forward with a comment reaches the bot as several messages but is one task. Parsing runs on Replicate with an **open** model (`REPLICATE_LLM_MODEL`, default `qwen/qwen3-235b-a22b-instruct-2507`; ~1–9 s, well under a cent) and voice on `openai/whisper` pinned by version (`REPLICATE_WHISPER_VERSION`, `language: ru`, the team's names as `initial_prompt`). Not Claude or GPT: their owners do not serve companies from a number of countries, a reseller does not change that, and the company is Russian. The model **suggests, code decides**: it sees the author's team, the projects and open top-level tasks the author can see (`projectScope`/`taskScope`, so an employee neither files into someone else's project nor learns their task titles through the bot) under short codes `P3`/`T12` rather than ids (an invented code simply matches nothing), plus a 14-day calendar with weekdays (without it «к среде» said on a Wednesday became today). Everything it returns is checked in `parse.ts`: names resolve to `team_members` (exact, then by stem for an unreduced case like «Камилю», only when exactly one person matches; the rest go to «не нашёл» on the card), codes must exist, a due date must be real and within two years and becomes 23:59:59 in `TIMEZONE` like the form's, and the priority falls back to `normal`. Creation goes through `createTask` in `crm/tasks/service.ts`, the very function behind `POST /tasks`, so the bot is no way around visibility, placement or «у подзадачи нет заметок»; a subtask's details become a note on its parent instead. The journal gets `diff.via = "telegram"` through `auditAs`, since there is no request. A list of items becomes subtasks, and a title matching an open task gets a warning on the card, not a refusal. The reply is a **card** (`cards.ts`) that holds no state: the task id rides in its buttons and every press re-reads the task, so CRM edits and server restarts never desync it. «Отменить» is the usual soft delete (then «Вернуть»), «Исполнители» toggles people; only the author or an admin may press, and the author must still be able to see the task, otherwise someone taken off a parent could re-add themselves to their old subtask with a stale button — the exact move `access.ts` closes. Notifications go out **60 s late** (`NOTIFY_DELAY_MS`), so a cancel or a fixed assignee lands before anyone is pinged; they go through the ordinary `notifyTask`, minus the author and, for a subtask, minus the people already told about its parent; stopping the bot sends whatever is waiting. Without `REPLICATE_API_TOKEN` `canIntake` is false and the bot behaves exactly as before; the card buttons still work, since they need only the database. The bot registers its own command menu on every start (`setMyCommands`, separate lists for private chats and groups, `/task` only when intake is on), so a change in code reaches Telegram without @BotFather; a failure there is logged and never stops polling. A bare `/task` (what tapping it in the menu sends) gets a hint instead of a parse, unless it replies to a message, which turns that message into a task. `/tasks` (`notify/my-tasks.ts`) lists everything open on the person, private chat only: their tasks and subtasks under `taskScope`, minus closed, hand-archived and subtasks of an archived parent, grouped as overdue / today / the rest by priority, each title a link into the CRM card; `/today` answers «what is burning», this one «what is on me», which is where an undated task gets remembered. What leaves for Replicate is the message, the team's first names and the author's project and task titles: no clients, no money.

CRM tables live in the same schema (`Lead`, `Client`, `Project`, `ProjectStage`, `Invoice`, `Task`, `Credential`, `Note`, `TeamMember`, `JobRun`). What matters most on a lead is the **next step** — `nextActionAt` plus `nextActionNote`: statuses never remind anyone of themselves, so an overdue next step is what puts a lead into the «Просрочено» tab of the leads screen, and the note is what makes that reminder actionable without opening the card. Closing a lead (`won`/`lost`) clears both server-side. A lead has no "done" status by design — it is an inquiry, not work; it ends as `won` (becomes a Project) or `lost`. `Lead.service` holds a `SERVICE_PAGES` key, duplicated with labels in `crm/src/lib/services.ts` because the two apps build separately. `Task.projectId` is nullable on purpose: plenty of real tasks belong to no project. Every amount is stored **in minor units** (копейки/центы) as an integer — `Project.monthlyAmountMinor`, `Invoice.amountMinor`, `ProjectStage.amountMinor`, `Credential.amountMinor` — because binary floating point cannot represent 0.1 + 0.2 exactly and money eventually drifts by a kopeck; the `Minor` suffix is deliberate, since a field that silently changed meaning would render every missed call site 100× too large. Conversion happens only at the edges (`parseAmount`/`amountToInput`/`money` in `crm/src/lib/money.ts`). Each amount also carries its own `Currency` (`rub`/`usd`) rather than the system having one currency, because some work is billed in dollars. The rule that follows is load-bearing: **amounts in different currencies are never summed** — the CRM has no exchange rate and inventing one would make yesterday's total a lie tomorrow — so totals are one number per currency (`sumByCurrency`/`formatTotals` in `crm/src/lib/money.ts`, mirrored in `server/src/crm/currency.ts`). `Credential.projectId` is nullable and `SetNull` on delete — a closed project must not take the hosting password with it when the site it served is still running; the Доступы screen groups by project, with unattached (shared email, GitHub) last, under a «Закреплённые» group. Pins are personal (`CredentialPin`, one row per admin and credential), so `GET /credentials` returns only the viewer's `pinnedAt`, and a pinned record leaves its project group rather than appearing twice. `Note` is one polymorphic table for all four entities (`entity` + `entityId`, no FK) rather than four comment tables.

**Credentials (`Credential.passwordEnc`):** the CRM stores service passwords encrypted **on the server** with AES-256-GCM (`server/src/crypto/sealed.ts`) under `VAULT_KEY`, 32 bytes of base64 that lives only in the environment: never in the database, never in a dump. The row id goes into the AAD (`credential:<id>`, `totp:<userId>`), so a ciphertext copied into another row does not open. The browser vault with a shared master passphrase is gone, and the owner revoked the old ban on server-side decryption: a password must open with a personal 2FA code, not with a phrase the whole team knows. Writes arrive as plaintext over HTTPS and are sealed on the server. Lists and cards never carry a password, only `hasPassword` and `legacyPending`; the one way out is `POST /credentials/:id/reveal`, which needs 2FA enabled and either a TOTP code or a live 10-minute confirmation window kept on the session row (`sessions.two_factor_confirmed_until`). Recovery codes do not count. Every reveal writes `audit_log` first and decrypts second, through `prisma.auditLog.create` rather than `audit()`, which swallows errors: no log row, no password. Deleting a credential is a soft delete, but it nulls `passwordEnc` outright, so a restored credential comes back without its password.

**Search (`src/crm/search/`):** one `GET /search` sweeps clients, projects, tasks, credentials and the polymorphic `Note` table (minus notes on leads), capped per entity. It matches substrings case-insensitively rather than using Postgres full-text, because FTS without a Russian morphology dictionary fails the common case — «Казан» would not find «Казани». Hits from notes are resolved back to the record they belong to and de-duplicated against direct hits, so one card never appears twice. Cards have no routes of their own (screens open them in modals), so a result navigates to `/<entity>?open=<id>` and `useOpenFromSearch` (`crm/src/lib/open-from-search.ts`) opens it once the list has loaded, then clears the param — otherwise the card would reopen on every refresh. An archived project is not in the loaded list, so the projects screen passes `fetchMissing` and the hook fetches that one card. An employee searches only visible tasks, projects and their notes, and never clients or credentials; the scope sits in the query rather than filtering the result, otherwise other people's rows would eat the per-entity cap. A subtask hit opens its parent, and a subtask whose parent is deleted or not visible is not found.

**Trash (`src/crm/trash/`):** every soft delete (`Case`, `Lead`, `Client`, `Project`, `Task`, `Credential`) is a 30-day grace period, not a graveyard. Nothing used to read `deletedAt` rows back — there was no restore path at all — so deleted data simply accumulated in every nightly dump, including lead contacts that 152-ФЗ expects to be removed once their purpose is served. `TRASH` in `trash/registry.ts` is the single list both the `/trash` screen and the daily `purgeDeleted()` job (wired into the existing cleanup interval in `server.ts`) work from; adding a soft-deletable model means adding one entry there. Hard deletion is safe because every relation already declares `onDelete` (`Cascade` or `SetNull`), so the database untangles references itself. Notes are deliberately **not** deleted when their entity is — they are removed at purge time, otherwise restoring a project would silently return it without its discussion.

The reason passwords are allowed in the CRM at all has not changed: nightly `pg_dump` backups leave the machine, and a dump without the key is worthless. So the key must never reach the database, a log or `backup.sh`, which snapshots only the database and images. Keeping one key on the server has load-bearing consequences. Whoever holds both `.env` and a dump holds every password. The key is permanent, because there is no re-encryption tool. Losing it loses the passwords and TOTP secrets (recovery codes still let people in, `user:reset-2fa` clears 2FA, passwords are re-entered), which is why a copy lives off the server. Without `VAULT_KEY` the API runs and `reveal` answers 503 `vault_unavailable`. A key that does not match the data is caught at startup by `checkVaultKey`, which logs an error and does not crash: a typo would otherwise surface only at the next reveal, with new passwords already sealed under the wrong key and two generations of ciphertext in one column. `reveal`, `legacy`, `migrate` and `/telegram/link-code` also pass `requireCrmOrigin`: the cookie is shared with the site, and now that the server decrypts, a stored XSS on the site could otherwise reach the passwords of anyone with an open confirmation window. `CRM_ORIGIN` turns that check on.

The old `Credential.secret` is frozen: nothing writes to it any more, not even a soft delete, and it stays as the fallback for an API rollback. Passwords move once, through the «Перенести пароли» button in Доступы: the person types the old passphrase, the browser (`crm/src/lib/vault.ts`, PBKDF2-SHA256 → AES-GCM-256) decrypts what `POST /credentials/legacy` returns, and `POST /credentials/migrate` hands the plaintext to the server to seal. `legacy` is a password view like any other, so it sits behind the same second factor and writes the same journal. `migrate` keeps its condition inside `updateMany` rather than checking first, otherwise a password saved in another tab would be overwritten by the old one. `secretMigratedAt` records that the fate of the old value is settled: `secret` is never cleared, so without it an erased password would return on the next migration. `POST /vault` and `/vault/reset` answer 410. No passphrase means re-entering the passwords; new ones work without it.

**Two-factor login (`server/src/auth/two-factor.ts`, `totp.ts`):** TOTP per RFC 6238 (30 s, 6 digits, ±1 step) on `node:crypto`, per user, connected in Settings by QR, with 10 one-time recovery codes stored as SHA-256. The TOTP secret is sealed with `VAULT_KEY`. Login is two steps and **shared with `/panel`**, so both `crm/src/screens/login.tsx` and `src/lib/admin/auth.ts` with `admin-panel.tsx` implement the second one. With `totpEnabledAt` set, `POST /auth/login` creates no session and returns a 5-minute one-time `ticket` (only its hash is in `login_tickets`; the browser keeps it in component state); `POST /auth/login/2fa` takes the ticket plus a TOTP or recovery code. `totpLastStep` forbids reusing a code inside the ±1 window. Five wrong codes in a row lock TOTP for 15 minutes; the counter lives on the user row and is checked inside a transaction with `SELECT … FOR UPDATE`, since an IP limit stops neither parallel requests nor many addresses. A lockout is sent to admins privately: it means someone already has the password. Recovery codes work during a lockout and without `VAULT_KEY`, otherwise whoever knows the password could keep a person locked out. Connecting takes the password at `setup`, but `enable` does not, so an abandoned setup must not leave a stolen cookie a code to guess: `enable` counts wrong codes under the same row lock, the fifth wipes the unfinished secret, the secret expires 15 minutes after `setup` (`totpSetupAt`), and «Отмена» erases it through `POST /auth/2fa/cancel`. After any of these only the password gets back in. The login condition is `totpEnabledAt` alone, deliberately not `canVault`: a missing key closes TOTP with 503 rather than waving people through. A ticket proves the password only at the moment it was issued, so it is deleted on `disable`, on disabling the account, by `user:reset-2fa` and by `user:create`. 2FA is not mandatory, so nobody gets locked out of work, but passwords do not open without it, and the CRM shows a banner until it is on. Losing both the phone and the codes has one exit, the CLI `npm run user:reset-2fa`; a screen for it would be a way around the second factor with a stolen admin session. `GET /auth/me` and both login responses go through `toUserDto`, an explicit field list: `resolveAuth` reads the whole `users` row, including `passwordHash` and `totpSecretEnc`.

**Roles and visibility (`server/src/crm/access.ts`, `server/src/auth/guard.ts`):** two roles, `admin` and `employee`, mapped onto the old enum values `owner` and `editor` (`@map` in the schema), so an API rollback needs no SQL; `marketing` stays in the enum only because Postgres cannot drop a value, and no row uses it. `requireTeam` lets both roles into a section and leaves the records to `access.ts`; `requireAdmin` closes money, clients, credentials, the trash, leads, accounts and the site panel (`/cases`, `/posts`, `/service-catalog`, publishing) with 403. The CRM hides those sections and sends their addresses to `/`, but only the server is a real gate. An admin sees everything. An employee sees only their own work, and `access.ts` is the single place that says what that means, for routes, search, notes and Today alike: `taskScope` (assignee, author of a top-level task, or assignee of a subtask, and a subtask is also visible through its parent) and `projectScope` (leads the project or has a task in it). Authorship deliberately counts only on a top-level task: a subtask is created inside someone else's task while it is visible, and otherwise a person removed from that task would keep the subtask, put themselves back on it and reopen the parent and the project. Someone else's record answers 404, not 403, so the response does not confirm it exists. Both scopes are `OR` conditions and go through `AND: [...]`, because search also sets `where.OR`. Employee project responses are an explicit field list (`toEmployeeProjectDto`), without money, contract, hosting or the lead, and their task counts come from `projectRelationsFor(viewer)`, so the number matches the person's list and leaks nothing about other people's work. Note author e-mails are blanked for non-admins. The role is read on every request, so a demotion applies at once.

**Team (`server/src/crm/team.ts`):** an admin manages people, accounts, roles and Telegram usernames in one Settings block. Creating an account, disabling it or changing its role takes a `confirm` with the admin's password and, if they have 2FA, the second factor (`confirmAdmin`); otherwise a stolen admin cookie could create an account with a known password, attach its own 2FA and open every password. The last active admin and yourself cannot be disabled or demoted, and disabling revokes sessions and deletes login tickets in the same transaction. A username is saved in the person's row on Enter or blur with no `confirm`, since it grants no access, and `PUT /team/handles` changes only the people it is sent. An assignee is a person, not an account: `team_members.name` is the value stored in `developers[]` of tasks and projects, the list lives in that table rather than in code, and `assertDevelopers` answers 400 «Неизвестный исполнитель» to any other name. `team_members.user_id` links a person to an account; `resolveAuth` loads the link and `toUserDto` returns it as `memberName`, and an account without one owns nothing but what it created. The first word of a name was used once, by the migration, to make the first links. `POST /team/accounts` creates the account and the person in one transaction, and a person already linked to another account answers 409. A person may have no login at all, and «Создать вход» gives them one without creating a second person. Names are matched whole and case-insensitively, so the «Новый сотрудник» form offers «Создать вход» when the first word matches a person without a login: «Тимур Хакимов» next to «Тимур» would otherwise become a second person whose account does not open the old tasks. In the CRM `usePeople()` keeps the list for the tab until `forgetPeople()`; pickers offer only `active` people but keep one already picked.

**Board columns (`server/src/crm/columns/`, `crm/src/api/columns.ts`, `crm/src/components/column-menu.tsx`):** the status boards of tasks and projects are built from `board_columns`, which an admin edits in place: «…» in a column header renames, moves left or right, adds a column to the right of it (kind defaults to the neighbour's) and deletes. There is no add cell at the end of the board on purpose: it pushed the fourth column past the edge at 1440 with the panel open. A column is a title, a position and a `kind`, and the kind is the status its cards get, so everything that reads status (Today, the digest, billing, closing dates) works unchanged and three columns of kind `in_progress` are one status to the system. The kind is chosen at creation and never changes, because changing it would rewrite the status of every card in it and a project's status switches invoices on and off. The last column of a kind cannot be deleted (409), so every status always has somewhere to stand; a deleted column's cards go to the end of the first other column of the same kind with their status untouched. `columnId` beats `status` on write; a bare `status` (an old tab, Today's checkbox, subtasks) keeps a card in its column when the kinds match and otherwise puts it in the first column of the kind (`placeCard`). A card with no column, or one whose column was deleted meanwhile, is shown in the first column of its status (`columnOf`), and reorder claims such cards. Task columns are only `todo`, `in_progress`, `done`: cancelled is an outcome, not a stage, and subtasks never have a column. «Когда-нибудь» (`backlog`) is gone at the owner's request: the migration moved those tasks to the end of «К работе» and added «На проверке» (`in_progress`) in its place, and a `backlog` from an old tab becomes `todo`. Projects now open as the board from 768px, like tasks.

**Tasks and the board (`crm/src/screens/tasks/`, `crm/src/components/board.tsx`):** the screen opens as a board from 768px up and as a list below, because a phone has no drag; the view is not remembered. The board has two layouts, «По статусам» and «По проектам», and that choice is kept in `localStorage`. The project board (`project-board.tsx`) shows open tasks only, sorted by `byUrgency`, with a column for every project that has an open task, even a closed project, because an open task must not vanish. More tasks go left, ties go by title, «Без проекта» is always last, and a card shows a status badge instead of its project (none for `todo`). Dropping into another column `PATCH`es `projectId`, and the server moves the subtasks along; dropping inside a column does nothing, so no insertion line is drawn (`reorderable={false}`). The «+» of a column presets its project. Columns share the width as `minmax(16.5rem, 1fr)` with no ceiling: at 1440 with the panel open four of them fit. When they do not fit, the board scrolls sideways inside itself, not the page. A column reaches the bottom of `main` (measured, floor 320px), so a card can be dropped anywhere in it. `readOnly` turns dragging and «+» off for an employee's project board. `Task.description` stays in the table and the API only for an old tab during rollout: «Подробности» is gone from the form and the card, `valuesToTaskInput` omits the field so that saving cannot erase an old value, and the migration copied existing descriptions into notes.

Importance has four levels, `low`, `normal`, `important`, `high`, labelled Низкая, Обычная, Высокая, Срочно: a dropdown in the form, default Обычная. A new task has it next to «Проект»; a saved one gives «Проект» a full row, the only field with long values, and puts «Статус» and «Важность» side by side. `high` keeps meaning «Срочно» because it is older than the four levels: no row is rewritten, and an old tab and an API rollback keep working. `important` went in **before** it, and that had to be written by hand (`ADD VALUE … BEFORE`), since Prisma appends a new value last and `orderBy priority desc` in `today.ts` follows enum order; `byUrgency` follows `TASK_PRIORITIES` in the same order. An API rollback needs one `UPDATE` first, because a single `important` row fails the old Prisma client's whole read (`docs/deploy.md`); the rollout is API first, because an old API refuses `important` and silently drops `note`. `PriorityMark` (`crm/src/components/priority-mark.tsx`) is the one mark on a card, a list row and Today: a flame, a double chevron, a muted chevron, nothing for `normal`, nothing on a closed task.

Notes in the task window have no button and no hint: that is `savedWithForm` on `NotesPanel`/`NotesView`, while projects, leads and clients keep both. The text goes with the window's save, and ⌘Enter in the field passes through to the form, where `flush()` adds it. «В архив» and «Вернуть из архива» flush the same way and stay open with the error on a failure. The cross, Escape and a click outside cancel, like every other field. A new task keeps the text in the window and sends it as `note` on `POST /tasks`, written through `createNote` inside the task's own transaction, so neither exists without the other. `note` sits outside `taskFields`, so `PATCH` has no such field.

**Task archive (`archivedTaskWhere` in `server/src/crm/tasks/dto.ts`):** two ways in. A closed task (done or cancelled) goes there by itself three days after it was closed; that part is computed, not stored: no scheduler, and reopening a task clears `completedAt` and puts it back on the board, closing it again gives it three more days. Old closed rows without `completedAt` count from `updatedAt`. An admin can also archive any top-level task by hand, open ones too (`POST /tasks/:id/archive`, `/unarchive`, «В архив» / «Вернуть из архива» in the card): that is `Task.archivedAt`, and such a task also leaves Today, the digest and project task counts (`archivedAt: null` in Today's `liveTask` and in `PROJECT_RELATIONS`). Moving a task (status or column) clears `archivedAt`; editing the title does not. Unarchiving clears only the hand mark, so a task closed long ago stays archived by age and the card offers no return button: the circle that reopens it is the way back. A subtask cannot be archived on its own (400). `GET /tasks?archived=exclude|only|include` (default `include`, so an old tab sees everything) goes into `AND` like visibility, because search owns `where.OR`; `only` is ordered by `completedAt` desc, since the archive grows without end and the 1000-row cap would otherwise cut the recent ones. `TaskDto.archived` carries the flag. The tasks screen loads open plus non-archived closed tasks, the «Архив» tab loads separately and reloads with the list, and search includes the archive so a long-closed task is not created twice.

**Subtasks (`Task.parentId`):** one level deep, set only at creation; a subtask lives in its parent's project and the server moves it with the parent, so `PATCH` with another project on the subtask itself answers 400. `GET /tasks`, the board, Today, the digest, the calendar and project task counts show only the top level; `subtasks: { total, done }` is the progress on a card and `subtaskList` comes only with `GET /tasks/:id`. Deleting a parent is a soft delete that does not touch its subtasks: they become unreachable through it (`liveTask` in `access.ts`) and return with it, and physical deletion cascades through the FK, with `TRASH` removing their notes, which have no FK. A subtask deleted on its own sits in the Trash as a regular task, hidden there while its parent is deleted too. In the CRM (`subtasks.tsx`) every action saves at once and the interface offers only `todo` and `done`, ticked with the same round circle as a task row; a new task holds a draft with the same row (circle, title, assignee) and a visible «+» next to the field, creates the parent first, and if a subtask fails the task stays and the window reopens as an edit with the error; the note is already saved with the task by then, so that window loads it from the server and carries no draft over. `POST /tasks` with `parentId` and a non-empty `note` answers 400: a subtask has no window, so the note would be invisible.

**How a project pays:** `billingMode()` in `crm/projects/dto.ts` is the single rule, and the card, stage visibility, monthly documents, `unbilled()` and the stage checks all stand on it. `billingMonthly` or `workType === "support"` gives `monthly`, otherwise `contract` gives `stages`, otherwise `none`. The flag beats the contract on purpose: old contracts carrying it already have monthly invoices, and honouring both would show one project a monthly bill and «Этап 1 из 3» at once. `nextBillingMonthly()` changes the flag only when the work type actually changes, because the form sends both fields on every save: reacting to the field alone would switch the flag on for an old support project on a routine save and light up every month since it started. So on support a value sent without a type change is ignored, and the form does the same from its side: picking the same option does nothing, and returning to the saved type restores the saved flag.

**Contract stages (`project_stages`, `crm/projects/stages.ts`):** a contract is paid in three stages, strictly in turn, and the server enforces the order. Stages are a separate table rather than rows of `invoices`, for concrete reasons: `@@unique([projectId, kind, period])` rejects two stages in one month; adding a `stage` column to that key means replacing the index, and since NULLs are distinct in a Postgres unique index it would stop catching «two invoices for March»; Prisma cannot describe a partial index; `period = NULL` changes a NOT NULL column and breaks every reader of `period`. The table is purely additive, `@@unique([projectId, position])` makes creation idempotent, and the invoice routes never see a stage, so the payment order lives in one place. Both `PUT` amounts and `PATCH` payment run in a transaction under `SELECT … FOR UPDATE` on the project row: without it two simultaneous marks pass the check, and a payment landing mid-`PUT` changes the amount of a paid stage. The contract total is not stored, it is the sum of the stages; a second stored number would eventually disagree. Each stage keeps its own `currency`, since the project's can change and a paid amount must not change meaning. The price of two sources is paid once, in `crm/projects/bills.ts` (`listBills`), shared by `/invoices` and `collectToday()`. Scope `due` shows only the first unpaid stage of a contract: three at once would overstate the debt by the whole contract. `POST /projects/:id/invoices` with `kind: "invoice"` on a contract answers 409, otherwise an invoice raised for a stage out of habit would double the debt and bypass the order.

**Monthly documents (`crm/projects/monthly-documents.ts`):** at the start of each calendar month in `TIMEZONE`, every active, non-archived project with `billingMode === "monthly"` gets an invoice row and an act row for that month, with `monthlyAmountMinor`. An empty amount is a valid state, shown as «сумма не указана», and setting the amount later fills the current month's unpaid empty rows. These are records, not PDFs: a real document needs requisites, numbering and VAT. Only an invoice is paid: an act is a document, so its row shows the issue date and carries no paid badge or toggle. **The scheduler lives outside the bot** because invoices must not depend on `TELEGRAM_BOT_TOKEN`. The `job_runs` mark holds the month, not the day, and is written in one transaction with the rows: a failure halfway must not count the month as done, while a daily mark would resurrect a manually deleted invoice the next morning. Creation runs before the digest and waits for `DIGEST_TIME` on the 1st; from the 2nd the time check is off, and that is the catch-up after downtime. Past months are never backfilled: they stay in «Не выставлено». That includes months a project with records spent in the archive or on hold: no history of status is kept, so on return they count as missed. A project starting next month gets nothing yet. «Не выставлено» (`unbilled()`) counts only `active` projects, so the list matches what the system is obliged to bill: the form defaults to «Запланирован», and a planned project would otherwise raise the digest every morning. The «нет счёта» label on a card follows the same rule and also waits for `startedAt`. An old support project without the flag counts from its first record, and with no records from the current month: months before the automation were never tracked in the CRM. That month is kept in `Project.unbilledFrom`, set by `rememberUnbilledMonth()` when such a project becomes eligible (status or start change, return from the archive or the trash) or loses its only record (deleted, moved to a later month, turned into an act): the next run creates a record that would otherwise become the first one and silently drop the month. A record for a future month anchors nothing, for the same reason. While the project stays in work the mark does not move. If it leaves work with no record at all, the mark goes too: the record it guarded against never appeared, and a project activated by mistake and started for real months later would otherwise count the whole idle stretch as missed. Nothing counts before `startedAt`, with or without records. The private message to admins is built from the rows actually created, because `skipDuplicates` may have skipped one a person added a moment earlier, and is cut by length through `fitMessage` (shared with the digest): the month mark is already set, so a text Telegram refuses would never be sent again.

**Archive (`Project.archivedAt`):** a flag, not a status: an archived project keeps its outcome («сдан», «отменён»), and the status speaks about the work, not about whether it is shown. Archived projects leave the board, Today, the digest, «Не выставлено» and monthly documents, and their tasks leave Today and the digest. They remain findable in search and in the «Архив» tab, and their invoices stay in Счета, because a debt does not vanish with archiving. Renewals of their credentials stay in Today on purpose: the site keeps running. `GET /projects` excludes the archive by default, so every old caller is correct without changes.

**Today (`collectToday()` in `server/src/crm/today.ts`):** the single source for the Сегодня screen and the digest, so they cannot diverge. It takes an optional `developer`: tasks and projects narrow to that person, and unassigned tasks disappear, because the filter answers «what is on me». The morning digest builds on it through `personalSnapshot` (own tasks and projects, plus team-wide money for an admin) and `unassignedSnapshot` (the team chat), see Notifications. `collectTodayFor(viewer, developer)` decides what a person gets: an admin gets the team and may narrow it to any name, an employee always gets themselves with `workOnly` (no money, renewals or «не выставлено») whatever the query says, and an account with no linked person gets an empty snapshot rather than the team's. A personal `/today` passes that snapshot to `buildDigest`.

**Leads are admin-only and off the menu.** The owner asked to remove the section, so an admin reaches it only by the direct `/#/leads` address, and an employee gets 403. The table, API, trash and `notifyNewLead` stay, but leads are gone from the menu, Today, the digest and search. The `leads` key in `GET /today`, `scope=unpaid` in `GET /invoices` and the `secret` field in `/credentials` exist only for an old CRM tab during rollout and are removed in the next release.

Three things that bite and are easy to miss: `server/.env` is only loaded because the `dev` script passes `--env-file-if-exists` (Prisma otherwise reads it for `DATABASE_URL` alone, and every other var silently falls back to its zod default); and any HTTP verb the panel or CRM uses must be listed in the CORS `methods` array in `src/app.ts` — a missing verb is blocked at the browser preflight and surfaces as "server not responding", which curl can never reproduce. On a machine where another Postgres already listens on `127.0.0.1:5433`, the `localhost:5433` from `.env.example` reaches that server instead of the Docker one and Prisma fails with `P1010`; `server/README.md` has the workaround.

**Page frames:** The homepage builds its own frame inline in `page.tsx` (it owns the preloader). Subpages use `SiteShell` (`src/components/layout/site-shell.tsx`), which passes `sectionPrefix="/"` to the header so nav links point back to homepage `#anchors`. Both wrap content in `SmoothScrollProvider` (Lenis) + `ContactModalProvider`.

**Contact channels:** Defined once in `CONTACT_CHANNELS` (`src/lib/constants.ts`). Each channel has an `action`: `"link"` (open directly — Telegram/WhatsApp) or `"copy"` (show a popover with a copy button — phone/email/MAX, which have no chat link). `withStarterMessage()` appends a pre-filled `?text=` draft, but only for Telegram/WhatsApp. `ORG`/`SITE` constants also hold legal entity data used in structured data.

**3D & animation:** three.js / react-three-fiber power the hero logo and per-service hero scenes. This stack is **always** loaded via `dynamic(() => ..., { ssr: false })` and guarded by a `WebGLBoundary` error boundary + a runtime `hasWebGL()` check, falling back to a static component (see `hero-logo.tsx`, `service-hero-visual.tsx`). Service hero variants map to scenes in `src/components/service-hero/scenes/` — one per service, wired in three places: the `ServiceHeroVariant` union, the `SceneForVariant` switch and `HERO_VISUAL` in `service-page-content.tsx` (the static fallback is generic, so no per-variant artwork is needed). The series holds together on two rules worth keeping: every scene is polished chrome with **exactly one brand-green element**, and every metaphor is used once — a padlock, a shield, a gear pair and a hub-with-satellites are already taken, so a new scene has to find its own image rather than reuse a neighbour's. Motion uses Framer Motion + GSAP/ScrollTrigger + Lenis smooth scroll.

**Reduced-motion / device gating:** `src/lib/utils.ts` exports `prefersReducedMotion()`, `canUsePointerEffects()` (desktop + fine pointer + no reduced-motion), and `cn()` (clsx + tailwind-merge). Gate all magnetic/tilt/parallax pointer effects behind `canUsePointerEffects()`.

**Styling:** Tailwind CSS 4 configured entirely in `src/app/globals.css` via `@theme inline` (there is no `tailwind.config`). Design tokens (colors, radii, section spacing, container width) are CSS variables defined there — the brand accent is `--accent: #b4e02d`. Fonts: Manrope (sans) + Unbounded (display), loaded via `next/font/google` in `views/fonts.ts` with Cyrillic subsets.

The layout is drawn for **1920 wide** and scales down proportionally on laptops: fluid tokens reach their maximum at 1920 (`vw = max px / 19.2`), and from 1024px up the root font-size follows the viewport (16px at 1920, floor 14px), so everything in rem — spacing, buttons, cards, text — shrinks with it. A token that caps at 1400–1600 instead makes a 1440 laptop look _bigger_ than a 1920 monitor; that was a real complaint. Avoid fixed `px` heights on blocks (use rem or a `min(…px, …vw)`), and never name a utility `text-*`: `cn()` runs tailwind-merge, which treats unknown `text-foo` as a colour and drops it next to `text-foreground`. Reading columns (article, privacy) are fixed-width and use `heading-article` / `heading-article-section` instead of the page-width heading sizes.

Blog covers are AI-generated, and every article says so in a caption under the cover (`blog.coverAiNote`). A translation may override `cover` when the art has text drawn into it.

**SEO:** `layout.tsx` `generateMetadata` reads the `meta.*` catalog block; per-service pages emit `Service` / `BreadcrumbList` / `FAQPage` JSON-LD inline; `StructuredData` (`src/components/seo/structured-data.tsx`) emits org-level structured data. Keep `NEXT_PUBLIC_SITE_URL` correct — it feeds canonical URLs and OpenGraph.

## Environment

Copy `.env.example` → `.env.local`. All vars are public `NEXT_PUBLIC_*` (no secrets in the project); they configure the site URL and contact channel targets. Because the site is a static export, these are baked in at build time. The one non-public secret is `FTP_PASSWORD`, used only by the deploy script.

## Conventions

- Prettier: 2-space indent, double quotes, semicolons, trailing commas, `printWidth: 90`, with `prettier-plugin-tailwindcss` (class sorting). Run `npm run format` before committing.
- Server Components by default; add `"use client"` only for interactivity/animation/3D.
- Images are hand-optimized to WebP/AVIF and committed under `public/` — there is no image optimizer at runtime.
