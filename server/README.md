# API администрирования

Бэкенд панели `/panel` и CRM: кейсы, статьи блога и каталог услуг в PostgreSQL,
проекты, задачи, счета и доступы, вход по почте и паролю со вторым шагом, публикация
снапшота на сайт, бот в телеграме. Архитектура и причины решений — в
[../docs/backend.md](../docs/backend.md).

Сайт остаётся статическим экспортом. База — источник правды для редактирования,
`content/cases.json` и `content/blog.json` — снапшоты, которые уезжают в
репозиторий при публикации и из которых собирается статика. Поэтому кейсы и
статьи по-прежнему предрендерены в HTML, а падение API не роняет сайт.

## Запуск локально

Нужен Docker (Docker Desktop на Windows) и Node 22+.

```bash
cd server
cp .env.example .env      # значения по умолчанию годятся для локальной работы
docker compose up -d db   # поднять только PostgreSQL

npm install
openssl rand -base64 32               # вписать в .env как VAULT_KEY, см. ниже
npx prisma migrate deploy             # накатить готовую миграцию (таблицы)
npm run seed                          # перенести content/cases.json и content/blog.json в базу
npm run user:create -- you@example.com admin   # пароль спросит интерактивно
npm run dev                           # API на http://localhost:4000
```

Затем в корне проекта:

```bash
# .env.local
NEXT_PUBLIC_ADMIN_API_URL=http://localhost:4000
```

и `npm run dev` — `/panel` откроется с формой входа вместо поля для токена.

Весь стенд целиком (API в контейнере) — `docker compose up`. Учтите, что без
аргумента compose ещё и пересобирает образ API — это несколько минут. Для
обычной разработки хватает `docker compose up -d db`, а API запускается через
`npm run dev`.

Для CRM (`../crm`) в `.env` нужен её origin, иначе браузер не пропустит запросы
с кукой:

```
WEB_ORIGIN=http://localhost:3000,http://localhost:5173
```

> `server/.env` подключается флагом `--env-file-if-exists` в npm-скрипте `dev`.
> Сам по себе файл не читается: Prisma грузит его только ради `DATABASE_URL`,
> поэтому раньше все остальные переменные молча оставались на значениях по
> умолчанию. Если добавите новый способ запуска — не забудьте флаг, иначе
> `WEB_ORIGIN`, `COOKIE_*` и лимиты из файла не подействуют.

> **Если порт 5433 занят чужим Postgres.** Docker публикует `*:5433`, но точный
> адрес петли его перебивает: когда на `127.0.0.1:5433` слушает, например, Homebrew
> `postgresql@16`, запрос на `localhost:5433` уходит в чужую базу, и Prisma падает с
> `P1010: User was denied access`. Проверить можно командой
> `lsof -nP -iTCP:5433 -sTCP:LISTEN`. Лечится подстановкой LAN-адреса машины вместо
> `localhost` в `DATABASE_URL` (на Маке `ipconfig getifaddr en0`): он доходит до
> контейнера. Адрес меняется вместе с сетью, поэтому при смене сети правку придётся
> повторить. В контейнер попали, если `select version()` показывает Alpine.

Бот и уведомления проверяются без настоящего телеграма: `TELEGRAM_API_BASE` указывает
на локальную заглушку Bot API, `TELEGRAM_TEAM_CHAT_ID` — любой идентификатор, токен —
любая строка.

## Проверка

```bash
curl http://localhost:4000/health          # {"ok":true}
```

Снапшоты `/cases/snapshot`, `/posts/snapshot` и `/service-catalog/snapshot` закрыты
ролью (`requireAdmin`): без куки ответ 401, сотруднику 403. Посмотреть их можно из
открытой сессии панели.

## Публикация

`POST /cases/publish` собирает снапшот и коммитит его вместе с новыми картинками
в репозиторий сайта, GitHub Actions пересобирает статику и заливает её по FTP.

Без `GITHUB_TOKEN` публикация работает «вхолостую»: снапшот собирается и
валидируется, но никуда не отправляется — так и задумано для локальной работы.

Токену нужны права `Contents: read and write` на один репозиторий сайта. Он живёт
только в `server/.env` и в браузер не попадает — в этом главное отличие от режима
без бэкенда.

## Маршруты

Кто может: «все» — без входа, «вошедшие» — любая действующая сессия, «команда» — `admin` и
`employee`, `admin` — только админ. Проверка стоит на сервере: скрытый пункт меню от прямого
запроса не защищает. В базе роли лежат старыми значениями `owner` и `editor`, чтобы откат API
обходился без SQL; в коде и API их нет.

Сотрудник видит своё. Задача своя, если он исполнитель, автор задачи верхнего уровня или
исполнитель её подзадачи. Проект свой, если он его ведёт или в нём есть его задача. Чужая запись
отвечает 404, а не 403: ответ не подтверждает, что она есть. Правило одно, в
`src/crm/access.ts`, на нём стоят маршруты, поиск, заметки и «Сегодня». Проект приходит сотруднику
без денег, договора, хостинга и лида, а `taskCount` и `openTaskCount` считают только его задачи.
Почта автора заметки у него пустая.

админа. `GET /tasks?developer=<имя>` находит и задачу, где человек исполнитель подзадачи.

только для этого сохранения; админам лично он пишет всё равно. Поле не хранится.

**Колонки досок**

| Метод         | Путь                   | Кто может |
| ------------- | ---------------------- | --------- |
| GET           | `/board-columns`       | команда   |
| POST          | `/board-columns`       | `admin`   |
| PATCH, DELETE | `/board-columns/:id`   | `admin`   |
| PUT           | `/board-columns/order` | `admin`   |

Колонка — это название, порядок и тип (`kind`), а тип — статус её карточек: у задач `todo`,
`in_progress`, `done`, у проектов все пять статусов. Задачи и проекты принимают `columnId`, и
он сильнее `status`. Один `status` без колонки оставляет карточку в её колонке, если та того
же типа, иначе ставит в первую колонку типа. `backlog` больше не колонка: такой статус от
старой вкладки становится `todo`. Тип после создания не меняется. Последнюю колонку типа
удалить нельзя (409), карточки удаляемой уходят в конец первой другой колонки того же типа,
статус у них прежний. `PUT /tasks/reorder` и `/projects/reorder` принимают `columnId`, а
`status` остался для старой вкладки на время выката.

`GET /cases`. Если контент успели изменить в другом окне, придёт `409`, и правки
не затрут чужие.

Что важно знать о маршрутах CRM:

- `POST /tasks` и новые исполнители в `PATCH /tasks/:id` шлют сообщение в фоне: сотруднику
  тэгом в общий чат, админу лично. Ошибка телеграма на ответ не влияет. Подзадача без
  исполнителя молчит, а кнопка в сообщении о подзадаче ведёт на родителя.
- `POST /projects` пишет лично всем админам, новый админ в `developers` у
  `PATCH /projects/:id` получает личное сообщение. В общий чат проекты не идут. Туда же,
  лично админам, уходят полная сводка, счета за месяц, лиды и блокировки входа. Запасного
  пути в чат нет: админ без подключённого бота этих сообщений не получит.
- Подзадача берёт проект родителя и уровень у неё один: подзадача подзадачи отвечает 400,
  чужой родитель 404, а `PATCH` с другим проектом у самой подзадачи 400. Смена проекта у
  родителя переводит и подзадачи. `GET /tasks` отдаёт только верхний уровень и
  `subtasks: { total, done }`.
- `developers` в задачах и проектах сверяются с `team_members`: другое имя отвечает 400
  «Неизвестный исполнитель». Фильтры `developer` — обычная строка.
- `PUT /tasks/reorder` применяет только видимые задачи этой колонки, и они меняются
  местами, которые уже занимали: чужие задачи не сдвигаются.
- `GET /today` сотруднику всегда отдаёт его самого: параметр `developer` не действует, блоки
  денег и продлений пустые, а учётка без связанного человека получает пустой срез.
- `GET /search` сотруднику ищет только по видимым задачам, проектам и заметкам к ним.
  Подзадача в выдаче ведёт на родителя.
- `POST /telegram/link-code` принимает `{ password }`, лимит 10/5 мин, только из CRM:
  привязанный чат читает `/today` мимо сессий. Привязка и отвязка видны в `audit_log`
  (`telegram_link`, `telegram_unlink`), смена пароля и включение 2FA снимают её. Команда
  `/today` в общем чате даёт урезанную сводку без денег и работы только админов, в личном
  чате админа полную, а в личном чате сотрудника только его работу без денег. В группе,
  которая не общий чат, команда отказывает.
- `PATCH /projects/:id/stages/:position` проверяет порядок оплаты под блокировкой
  строки проекта: этап N+1 нельзя отметить раньше N, снять N при оплаченном N+1 нельзя,
  ответ 409. `PUT /projects/:id/stages` принимает `{ totalMinor }` или `{ amounts }`.
- `POST /projects/:id/invoices` с `kind: "invoice"` у договора отвечает 409: договор
  платится этапами. Акты разрешены.
- `POST` и `PATCH /team/accounts` требуют `confirm`: пароль админа и, если у него
  включена 2FA, код или действующее окно подтверждения. `POST` создаёт учётку и человека одной
  транзакцией, а если человек уже связан с другой учёткой, отвечает 409. `PATCH` принимает
  `disabled` и `role`: себя и последнего действующего админа нельзя понизить или отключить,
  ответ 409.
- `GET /team/handles` отдаёт `name`, `telegramUsername`, `active`, `role`, `hasAccount`, без
  почт. `PUT /team/handles` меняет только присланных людей и подтверждения не требует.
- `GET /today` с ключом `leads`, `GET /invoices?scope=unpaid` и поле `secret` в
  `/credentials` остаются только ради старой вкладки CRM на время выката. Удаляются
  следующим релизом.

## Что важно при переезде на сервер

- `COOKIE_SECURE=true` и HTTPS — иначе сессионная кука уйдёт открытым текстом.
- `WEB_ORIGIN` — точные адреса сайта и CRM через запятую: с `credentials`
  браузер не примет `*`.
- `VAULT_KEY` — `openssl rand -base64 32`, задаётся один раз и до первого старта новой
  версии. Копию держать вне сервера: потеря ключа — потеря паролей.
- `CRM_ORIGIN` — точный адрес CRM: только с него открываются пароли.
- `COOKIE_DOMAIN` — если API живёт на поддомене (`api.it-optimization.ru`).
- Бэкапы `pg_dump` по расписанию и проверка, что дамп восстанавливается.
- Картинки лежат в томе `uploads` — его тоже надо бэкапить до первой публикации.

## Вход и учётки

Пароли входа хранятся как Argon2id, минимальная длина — 12 символов. Сессии серверные:
в куку уходит случайный секрет, в базу — только его SHA-256, поэтому доступ
отзывается мгновенно (`revokedAt`), а дамп базы не даёт войти.

`npm run user:create -- <почта> [admin|employee] [--name "Имя"] [--enable]` создаёт учётку
или меняет пароль существующей, и правила у него такие:

- смена пароля закрывает все открытые сессии, удаляет билеты входа и снимает привязку
  телеграма: чат читает сводку мимо сессий, и подключать его надо заново;
- роль меняется только при явном втором аргументе. Без него сброс пароля роль не трогает, но
  новая учётка без него становится `admin`, поэтому при создании роль указывать всегда;
- отключённая учётка включается только с флагом `--enable`;
- `--name` связывает учётку с человеком так же, как экран «Команда»: человека нет — заводит,
  есть без учётки — связывает. Без связи сотрудник видит только созданное им самим. Человек
  уже связан с другой учёткой — отказ, ничего не меняется. Учётка уже связана с другим
  человеком — связь остаётся, скрипт предупреждает и завершается с ошибкой;
- последнего действующего админа понизить нельзя;
- 2FA скрипт не снимает: забытый пароль не повод. Если учётка переходит к другому
  человеку, нужен ещё `user:reset-2fa`, иначе вход останется за старым телефоном.

На сервере то же самое — `npm run user:create:prod` внутри контейнера.

## Двухфакторный вход

TOTP (RFC 6238: 30 секунд, 6 цифр, окно ±1), подключается каждым для себя в Настройках
CRM. Вход общий с панелью, поэтому второй шаг работает и там. При включённой 2FA
`POST /auth/login` не создаёт сессию и отдаёт билет на 5 минут, а сессию создаёт
`POST /auth/login/2fa` с билетом и кодом. Повторно тот же код не принимается. Пять
неверных кодов подряд блокируют TOTP на 15 минут, и об этом приходит сообщение в общий
чат: значит, пароль уже знает кто-то чужой. Коды восстановления работают и при блокировке,
и без `VAULT_KEY`.

Подключение начинается с пароля (`setup`), а подтверждается только кодом (`enable`),
поэтому незавершённый секрет не висит без срока. Он стирается через 15 минут после `setup`,
по кнопке «Отмена» (`POST /auth/2fa/cancel`) и после пятого неверного кода, о чём админам
лично приходит сообщение. Дальше снова нужен пароль: ответ 409 `setup_reset`.

2FA не принудительная, но без неё нельзя смотреть пароли.

Потеряны и телефон, и коды восстановления — единственный выход на сервере:

```bash
npm run user:reset-2fa -- <почта>                 # локально
npm run user:reset-2fa:prod -- <почта>            # в контейнере api
```

Экрана для этого нет намеренно: кнопка стала бы способом обойти второй фактор с украденной
сессией админа.

## Пароли сервисов

Пароли из раздела «Доступы» шифрует сервер: AES-256-GCM, ключ `VAULT_KEY` из окружения,
32 байта в base64. В базе и дампах ключа нет, поэтому утёкший дамп сервисы не отдаёт.
Списки и карточки пароль не отдают никогда. Открыть его можно только через
`POST /credentials/:id/reveal`: нужна включённая 2FA и код либо действующее окно
подтверждения, 10 минут в рамках этой сессии. Каждый просмотр пишется в `audit_log`, запись
идёт раньше расшифровки. Сотруднику раздел закрыт.

- Нет `VAULT_KEY` — API работает, `reveal` отвечает 503 `vault_unavailable`, вход с 2FA
  закрыт для всех, кроме кодов восстановления.
- Чужой ключ — при старте в логе ошибка `VAULT_KEY не подходит к записям в базе`, а
  `reveal` отвечает 503 `vault_key_mismatch`.
- `CRM_ORIGIN` задан — `reveal`, `legacy` и `migrate` принимаются только с этого адреса.
  Кука общая на домен, а сайт с панелью тоже стоит в `WEB_ORIGIN`. Пусто — проверки нет.
- Ключ постоянный: инструмента перешифрования нет, поэтому заменить его нельзя. Потерян —
  пароли и секреты TOTP не читаются. Коды восстановления дают войти, `user:reset-2fa`
  снимает 2FA, а пароли вводятся заново.

Колонка `secret` с паролями, зашифрованными в браузере старой мастер-фразой, заморожена:
в неё никто не пишет, она остаётся запасом на случай отката API. Разовый перенос делает кнопка
«Перенести пароли» в «Доступах»: браузер расшифровывает пароли по введённой фразе и
передаёт серверу.

## Когда человек уходит

1. Отключить учётку в Настройках → Команда. Это отзывает сессии и билеты входа.
2. Убрать человека из телеграм-чата команды: учётка над ним не властна.
3. Найти пароли, которые он открывал, и сменить их в самих сервисах. Отключение отзывает
   доступ, но увиденное обратно не забирает. Экрана журнала нет, поэтому запросом:

   ```sql
   SELECT c.service, max(a.created_at) AS last_seen
   FROM audit_log a
   JOIN users u ON u.id = a.user_id
   JOIN credentials c ON c.id::text = a.entity_id
   WHERE a.action = 'reveal' AND u.email = '<почта>'
   GROUP BY c.service;
   ```

4. Если у человека был доступ к серверу, он мог унести ключ вместе с дампом. Тогда менять
   надо все пароли в самих сервисах: смена `VAULT_KEY` без этого ничего не даёт.
